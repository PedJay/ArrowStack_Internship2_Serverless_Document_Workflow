# Decision Log

| # | Date | Decision | Options considered | Rationale |
|---|---|---|---|---|
| D1 | 2026-10-31 | **AWS**, same region as Project 1 (`ap-south-1`) | Azure Functions, GCP Cloud Functions | Same account, CLI setup and IaC style as Project 1. The handbook's suggested stack names Lambda first |
| D2 | 2026-10-31 | **Presigned S3 POST** for uploads (client → S3 direct) | Upload through API Gateway + Lambda (base64 body), presigned PUT | Avoids the 6 MB Lambda / 10 MB API GW limits and Lambda time spent on bytes. POST (not PUT) because its policy can enforce an **exact `content-length-range`** and the `Content-Type` |
| D3 | 2026-10-31 | **S3 → SQS → Lambda** (queue in between) | S3 → Lambda directly, EventBridge | The queue gives buffering, a concurrency cap, per-message retry and a **dead-letter queue** with an alarm. With direct S3 → Lambda async invoke, failed events are harder to see and redrive |
| D4 | 2026-10-31 | **DynamoDB on-demand** for metadata | RDS (from Project 1), S3 object tags only | Key-value access pattern, conditional writes for idempotency, $0 when idle, PITR backups. RDS would cost money 24/7 for a few hundred records |
| D5 | 2026-10-31 | Duplicate detection with a **conditional put on a `SHA256#` claim item** | Query a GSI on sha256 before writing | A GSI read then a write has a race (two identical uploads at once both look "new"). A conditional put is atomic |
| D6 | 2026-10-31 | Final status write is **conditional on `status = PENDING_UPLOAD`**. Order: copy → write → delete | DynamoDB transactions, a separate idempotency table | SQS and S3 events are at-least-once. This order makes every crash point recoverable by a plain retry (proved by `test_crash_after_copy_is_finished_by_retry`) |
| D7 | 2026-10-31 | **Detect type from magic bytes**, not filename or the declared Content-Type | Trust the extension, use `python-magic`/libmagic | The declared type is attacker-controlled. Stdlib-only signatures cover our 5 types with no native dependency to package for Lambda |
| D8 | 2026-10-31 | **No third-party runtime dependencies** (boto3 comes with the Lambda runtime) | pypdf, Pillow | Zip stays ~30 KB, no layers, no CVE surface. PDF/PNG/JPEG headers are simple to parse for the metadata we need |
| D9 | 2026-10-31 | **One bucket with prefixes** (`incoming/ processed/ quarantine/`) | Separate buckets per stage | Fewer resources. IAM is still scoped per prefix. The notification is filtered to `incoming/` so writes elsewhere can't loop |
| D10 | 2026-10-31 | Known bucket name `<project>-docs-<account>-<region>` | Generated name | Breaks the bucket ↔ queue-policy circular dependency (the queue policy needs the bucket ARN before the bucket exists). Globally unique thanks to the account ID |
| D11 | 2026-10-31 | **HTTP API** (API Gateway v2), routing inside Lambda | REST API, Lambda Function URL | HTTP API is ~70% cheaper than REST and supports stage throttling. Function URLs have no throttling or access logs |
| D12 | 2026-10-31 | **API key in Secrets Manager**, 5-min in-memory cache | API Gateway usage-plan keys (REST only), SSM SecureString, env var | Same pattern as Project 1. Rotation without redeploy. Constant-time compare |
| D13 | 2026-10-31 | **CloudWatch Embedded Metric Format** for business metrics | Log metric filters (Project 1), PutMetricData | No extra API calls or latency. Metrics carry the doc_id as a searchable property. 5 custom metrics stay inside the 10 free |
| D14 | 2026-10-31 | **arm64 (Graviton)**, api 256 MB / processor 512 MB | x86_64, 128 MB | About 20% cheaper per GB-second. 512 MB comfortably holds a 10 MiB file, and more memory also means more CPU for hashing |
| D15 | 2026-10-31 | Trigger `MaximumConcurrency: 2`, batch 5, batching window 0 (D21), visibility timeout 180 s (6× the function timeout) | Unlimited concurrency | Cost and blast-radius guard on a free-plan account. AWS recommends a visibility timeout ≥ 6× the function timeout for SQS triggers |
| D16 | 2026-10-31 | `MaxUploadBytes` parameter in bytes | `MaxUploadMb` × 1048576 | CloudFormation has no arithmetic. My first draft built the number by string concatenation, which was wrong. Caught in review before linting |
| D17 | 2026-10-31 | Processor gets **`s3:ListBucket`** | Leave it out | Without it, S3 returns 403 (not 404) for a missing key. A redelivered event for an already-moved file would then look like a permissions failure and retry into the DLQ |
| D18 | 2026-10-31 | Treat **any NUL-free content as text**, then validate UTF-8 strictly | Require UTF-8 at the sniffing step | Found in the local demo: a Latin-1 file was refused as "application/octet-stream", which doesn't help the uploader. Now the reason says "not valid UTF-8 (byte 3). Re-save the file as UTF-8" |
| D19 | 2026-10-31 | Notifications are **best-effort, at most once** | Fail the message if SNS fails | The document is already filed correctly. Retrying would reprocess for the sake of an email. A lost email is visible in the logs, and the outbox pattern is on the roadmap |
| D20 | 2026-10-31 | **Teardown takes an on-demand DynamoDB backup** and force-deletes the API-key secret | Rely on PITR, keep the secret | PITR is deleted with the table, so the backup plays the role of an RDS final snapshot. A deleted secret keeps its name reserved for 30 days, which would block a redeploy with the same stack name |
| D21 | 2026-10-31 | SQS trigger `MaximumBatchingWindowInSeconds: 0` (was 2) | Keep a batching window for fewer invocations | **Measured in the cloud:** with a 2 s window, documents waited ~21 s in the queue (EMF `EndToEndLatencyMs` ≈ 21,000 ms while `ProcessingDurationMs` was 93–610 ms). At this volume batching saves nothing. After the change, client-observed p50 dropped from **21.8 s to 1.2 s** (max 22.3 s → 2.3 s). Revisit if volume grows to many documents per second |
